# 换肤插件系统设计草案

日期：2026-11-08。关联 PA-019、PA-020。状态：建议方案，待用户确认产品范围和未决事项；未实现、未引入新依赖。阶段状态以 [总计划](../PLAN.md) 为准。

## 1. 结论与目标

建议单独设计“换肤插件”的数据契约和前端主题应用能力，产品上复用 Sydney 已有插件入口，不先建设另一套通用插件市场或可执行代码宿主。换肤与技能、MCP 连接器的能力和风险不同，需要独立的校验、预览、应用和回退规则；是否及如何接入现有插件安装流程，须在实现前核实并确定。

目标是将来允许用户安装、预览、启用、切换和卸载不同风格，覆盖应用基础颜色、聊天区域和有限的视觉变体；切换无需重启服务或重新构建界面。首轮建议先支持 PC/Web，桌面客户端可否共用需实测；原生手机端单独适配。主题包和用户自定义背景、用户及 Bot 文字颜色应能共存。

此处“插件”是可分发的换肤资源包，不意味着获得运行代码或访问聊天数据的能力。背景图片和文字颜色仍可独立设置，换肤包可提供默认视觉值；不会恢复已删除的旧气泡数据或旧气泡编辑器。将来如果需要聊天气泡，可通过受限的内置视觉变体扩展，具体形态需另行确认。

## 2. 与现有系统的关系

- Web 当前使用 `packages/ui-tokens` 和 `apps/web/src/lib/ui-appearance.ts` 处理浅色、深色和跟随系统；聊天背景与双方文字颜色由 `apps/web/src/lib/chat-appearance.ts` 保存于当前浏览器 IndexedDB。
- 当前 `PluginPartSchema` 只包含 `connector` 和 `skills`，`apps/api/src/plugin-installs.ts` 安装技能及 MCP 连接器；尚无主题部件、主题包安装或前端主题宿主。
- 现有插件入口、来源预览、摘要核对等机制可以评估复用，但这些机制现针对现有部件，不能假定已支持主题包、离线安装或文件校验。
- 历史 [热插拔插件方案](HOT_PLUGIN_SYSTEM.md) 针对通用执行能力，不能直接视为换肤插件实现。主题包首版不需要进程管理、工具调用、模型权限或通用插件宿主。

## 3. 首版建议能力

1. 内置默认皮肤和一个示例皮肤；皮肤列表显示名称、作者、版本、适配情况及预览。
2. 支持预览、应用、取消预览、切换、卸载和恢复默认；切换仅影响展示，不改变聊天记录与业务逻辑。
3. 皮肤可定义经过白名单限制的浅色和深色视觉令牌，如页面、卡片、边框、主要文字、链接和强调色，以及受控的圆角与间距变体。实际支持哪些令牌，以实施前对现有界面的清点结果为准。
4. 可选本地主题图片作为皮肤背景；用户自己设置的聊天背景与双方文字颜色继续单独管理。主题包导入方式和是否首版开放第三方皮肤待决定。
5. 系统深浅模式改变时选择对应变体；变体缺失时按明确规则回退到当前应用默认主题，并提示皮肤不完整。

允许范围暂不包含任意 JavaScript、任意 CSS、远程图片、字体或脚本、替换组件、修改布局结构、读取消息和访问网络。更复杂的布局、动画、字体、图标或交互插件应另行设计，不应默认为声明式换肤包已有能力。

## 4. 包格式与应用流程

建议采用版本化声明式清单和随包静态资源；具体容器格式、文件扩展名、允许的令牌和大小限制待实现阶段确定。例如，以下仅说明结构，并非现有 API 或最终格式：

```json
{
  "schemaVersion": 1,
  "id": "example.ocean",
  "name": "海洋",
  "version": "1.0.0",
  "variants": {
    "light": { "colors": { "background": "#f4faff", "foreground": "#17324d" } },
    "dark": { "colors": { "background": "#102131", "foreground": "#e4f2ff" } }
  }
}
```

建议流程：选择来源 → 展示名称、版本、来源、变更和预览 → 校验清单与资源 → 用户确认安装 → 预览 → 显式应用并保存。安装与应用分开；若引入升级，在升级前对新的内容重新校验并展示差异。应用前构造完整可用主题并验证，失败时继续使用先前主题，避免部分应用。卸载当前皮肤时先回到默认主题，再清理该皮肤的本地资源；清理失败应提示，不影响用户背景。

建议保存已安装包、当前选择和资源在本地，具体存储结构及多标签页同步机制待设计；首版不承诺跨浏览器、跨设备或与账号同步。不要把个人背景图片复制进分享的皮肤包。涉及未来安装、备份或迁移方式时，同步运维文档。

## 5. 优先级和回退

建议按以下顺序决定最终效果，越靠前优先级越高：

1. 用户在聊天外观中明确设置的聊天背景、用户文字颜色和 Bot 文字颜色，各项互相独立。
2. 当前皮肤适用于当前深浅模式的视觉值及背景。
3. 当前应用对应深浅模式的内置默认值。

用户将某项设置恢复默认时，该项回到当前皮肤的建议值；若皮肤没有定义则使用应用默认值。切换皮肤不得清除用户覆盖值。预览期间临时显示所选皮肤，但不覆盖已保存皮肤及用户配置；取消或退出设置恢复原值。系统跟随模式、用户单项恢复默认、卸载当前皮肤、皮肤不完整、资源失效和浏览器存储失败均需单独验收。当前实现尚未接入此优先级模型。

## 6. 信任与兼容性边界

- 清单视为不可信数据；仅接受已知版本、已知字段和严格类型、范围及颜色格式；未知版本拒绝安装或要求升级应用，不能静默当作兼容。
- 资源必须属于包内且经格式、大小、数量与解码尺寸校验；禁止路径穿越、外部 URL 和主动加载远程内容。若将来引入压缩包，要限制解压后大小、文件数、重复路径和压缩比，避免资源耗尽；具体阈值待验证后确定。
- 不让主题包写入任意 CSS、HTML 或可执行代码，不让它读取聊天记录、令牌、账号或其他插件数据。渲染器只从经验证的令牌生成样式，主题包不能覆盖授权、安全提示及必要交互。
- 正文、按钮、焦点和状态需可辨认，主题应提供对比度提示及键盘、窄屏、浅深色适配；具体门槛和处理策略待确定。失效主题必须可从设置恢复默认。
- 明确包协议版本与应用版本兼容范围；升级、卸载、重复 ID、安装中断及旧版本回退不能导致设置损坏。主题的身份、来源和校验值不等同于安全保证。

## 7. 阶段与验收

| 阶段 | 范围与交付 | 验收条件 |
| --- | --- | --- |
| 0：设计确认 | 确定首版外观范围、来源、包格式、覆盖规则和 PC/Web 范围；盘点现有令牌及未令牌化样式 | 用户确认首版需求，兼容边界及未决项明确 |
| 1：本地主题内核 | 类型、严格校验、令牌映射、用户覆盖及默认回退；先用内置示例数据 | 单元测试覆盖无效包、优先级、深浅模式及失败回退；不接入执行代码 |
| 2：设置与生命周期 | 主题列表、预览、应用、取消、卸载；完成本地持久化和错误提示 | 覆盖重复打开、刷新、取消预览、删除当前主题、资源失效及存储失败；键盘与浏览器实测 |
| 3：插件入口与分发 | 决定并实现导入来源及现有插件入口接线，审核升级与卸载 | 确认来源、内容和兼容版本；异常包拒绝，安全边界及跨标签页行为完成验证 |
| 4：扩展 | 在实际需要后评估移动端、同步、市场、额外视觉变体 | 针对每项另行设计权限、存储迁移和真实设备验收 |

阶段顺序是建议，具体排期及实现授权待确定；所有阶段当前均未实施。

## 8. 待用户决定

2. 首版皮肤只由 Sydney 内置，还是允许用户导入本地主题包？是否计划对外分享？
3. 用户设置默认以当前浏览器为单位，还是将来需要登录后跨设备同步？
4. 首版只支持 PC/Web，还是同时覆盖原生手机端？
5. 插件入口放在现有插件页面、外观设置页面，还是两处互通？
