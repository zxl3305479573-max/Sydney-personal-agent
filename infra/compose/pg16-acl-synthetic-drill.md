# PostgreSQL 16 合成 ACL 恢复演练

`pg16-acl-synthetic-drill.sh` 只针对固定的本地缓存镜像
`sha256:aa6cb33cf4c19c765cefcf48d96176258800870a9a1e930ad126200f9d825139`
运行，缺少镜像时直接失败，不拉取镜像。仅在获授权的维护机执行：

```bash
/usr/bin/env -i PATH=/usr/sbin:/usr/bin:/sbin:/bin LC_ALL=C \
  /bin/bash -p infra/compose/pg16-acl-synthetic-drill.sh
```

必须以 root 在可信维护机运行，使用上述干净环境及 Bash 特权模式；不能用普通 `bash` 启动，因为它在脚本开始前可能执行 `BASH_ENV`。脚本文件和从根目录起的每个祖先目录必须由 root 拥有、不可由组或其他用户写入，且路径不含符号链接或原始 `..` 组件；文件还必须是单硬链接的普通文件。守卫在规范化路径前拒绝原始 `..`，避免与 Bash 解析符号链接及父目录的顺序不一致。

初始脚本及系统执行环境必须可信：启动后才运行的检查无法撤销恶意的初始脚本或 shell 已执行的代码，也不能证明初始 Bash 已读取的内容与守卫随后打开的内容相同。守卫逐级打开并核验路径，将读到的脚本内容复制到封存的内存文件，再从该快照重新执行，并输出快照 SHA-256；后续不按原路径重新打开脚本。脚本要求可验证本机 `/usr/bin/dockerd`、监听套接字、systemd 服务、进程启动时间和挂载命名空间，并固定套接字文件描述符，在每次 Docker 调用前后核验身份；无法验证时拒绝继续。系统管理员、systemd、Docker 守护进程和系统可执行文件均须可信；systemd 共享监听器不能证明每个请求的具体接收进程，也无法阻止特权进程并发篡改。

脚本不接受参数，创建两个全新容器，使用无网络、无宿主机绑定和 tmpfs 数据目录。数据库连接只使用容器内 Unix socket；脚本仅创建固定的合成角色、对象和数据。它使用管道传递归档，不保存归档文件。容器删除前核验名称、随机标签和镜像身份，删除后使用成功的容器列表检查不存在，不将 inspect 失败视为不存在。守护进程无法访问、身份不匹配、断言失败或清理失败均返回非零；只有检查和清理均成功才输出 `drill_and_cleanup=passed`。`SIGKILL`、主机崩溃或 Docker 故障可能阻止自动清理，须由维护人员依据输出的容器身份检查。

演练先以 `pg_dumpall --globals-only --no-role-passwords` 导出合成角色；由于目标预先具有同名引导管理员，流中仅过滤该管理员的 `CREATE ROLE`。再用 `pg_dump --format=custom` 恢复并检查表 owner、schema owner、schema USAGE、表 SELECT、成员继承的 SELECT、角色成员关系和合成数据七项，另外切换至合成读者角色实际读取。使用 `--no-privileges` 的对照中，先确认读取因 schema 权限被拒绝；然后仅向合成角色组补授 schema USAGE，确认读者仍无表 SELECT，实际读取被表权限单独拒绝。

这不是生产恢复方案：不同引导管理员的授权者问题、角色密码和密码哈希、PostgreSQL 18、加密备份链路、真实数据及跨源一致性均未在此演练中验证。全局角色脚本仍是禁用的候选，不能据此对生产集群执行操作。
