# 开发规范

状态：Sydney 协作基线；独立 Rakazo 试点的实际命令与结果见 [试点记录](rakazo-evaluation.md)。

计划、开发记录、验证结论和运维说明统一从 [docx/README.md](../docx/README.md) 进入。每完成一个可验收部分必须同步这些文档及受影响技术文档，未同步不标记完成；工作中断和失败也记录真实进展。当前推进设计和纯策略实现，本机只运行限定文件、单 worker 的离线验证，不启动服务或全量构建。

已确定：Agent 使用 TypeScript，PC 优先。按 [ADR-0003](adr/0003-rakazo-fork-as-execution-base.md) 试用 Rakazo 原有技术栈，保留其依赖锁文件与包管理器版本。当前固定提交在本机使用 Node.js 24.15.0、pnpm 9.15.0 完成依赖安装；不要绕过引擎校验或擅自升级上游依赖。

## 1. 工作流程

1. 明确任务关联的需求编号、实际行为和验收条件。
2. 阅读相关模块和已有测试，确定最小修改范围。
3. 实现改动；涉及设计取舍时同步记录 ADR。
4. 按改动风险执行验证，检查敏感数据和无关改动。
5. 交付具体改动、验证证据、已知限制和文档更新。

不将用户未要求的重构、依赖升级或新功能混入当前任务。未经明确要求，不自动创建分支、提交或推送。

## 3. 编码约定

- 使用能表达职责的英文名称，避免单字母变量和隐式共享状态。
- 核心业务与具体模型 SDK、界面框架和存储实现分离。
- 在系统边界校验模型输出、用户输入、工具参数和配置。
- 错误应提供稳定的类别、用户可理解的提示和可关联的任务编号。
- 不吞掉异常，不用空结果伪装成功，不把模型生成文本当成执行证据。
- 只引入当前场景所需的依赖，避免提前构建通用框架。
- TypeScript 开启严格类型检查，外部数据先校验再进入业务类型，不用宽泛的 `any` 绕过 Provider 契约。
- 供应商 SDK 只在 Provider 适配包使用，不从 PC 前端、Agent 核心或共享契约导入。
- 代码注释按任务要求添加；复杂设计优先在相关文档记录动机和约束。

## 4. 配置与数据

- 将默认配置、用户配置、密钥、运行数据分开管理。
- 配置示例只使用占位值，说明必填项、默认值和用途。
- 优先级统一为：显式启动参数 → 环境变量 → 用户配置 → 默认值。
- 启动时校验配置，不在运行中途才暴露必要配置缺失。
- M1 必须配置忽略规则，防止密钥、日志、会话、本地数据库和构建产物入库。
- 存储结构变化提供版本和迁移方式；有数据破坏风险时先提供备份和恢复路径。
- 不依赖写死的个人绝对路径，工作区和数据目录应可配置。

## 5. 测试与验证

| 层级 | 重点 | 典型验证 |
| --- | --- | --- |
| 单元测试 | 稳定的业务规则 | 状态迁移、参数校验、授权匹配、预算判断 |
| 集成测试 | 模块边界与持久化 | 工具执行、存储读写、记忆删除、重启恢复 |
| 场景验收 | 用户实际结果 | 代表性任务成功、失败、取消、授权拒绝 |
| 安全验证 | 数据和权限边界 | 路径越界、注入指令、脱敏、副作用重试 |
| Provider 契约验证 | 可替换性与能力差异 | 同一动作格式、错误分类、租约失效、不支持能力和过期处理 |

模型调用在常规测试中使用可控替身，测试结构化结果和行为，不断言整段生成文案逐字一致。真实模型测试单独启用，说明配置要求和成本，不作为普通验证的隐式步骤。

有副作用的外部工具在测试中默认使用隔离资源或替身，不能触及真实个人数据和账号。

验证从受影响范围开始。纯文档变更检查链接、术语、需求一致性和格式，不新增与行为无关的测试。

当前文档仓库没有应用测试命令。独立 Rakazo 仓库保留上游 TypeScript、Vitest 等验证入口；已执行项及结果在试点记录中单独列出，不把底座检查通过解释为 Sydney 需求验收通过。

## 6. 依赖与自动化

- 确定运行时和包管理方式后提交对应锁文件，记录支持版本。
- 为引入的依赖说明用途，优先选维护成本可控、许可证适用的方案。
- 自动化检查使用仓库中真实存在的命令，覆盖格式、静态检查和已有测试。
- 检查不依赖个人机器路径、私人账号或默认可用的付费模型密钥。
- 检查失败时说明是否由本次改动引起，不借机修复无关问题。

## 7. 变更评审

交付或评审说明至少包含：

- 改动解决的需求或问题，必要时提供输入和前后行为。
- 核心设计、权限或数据结构的变化。
- 实际执行的验证及结果，未执行项与原因。
- 影响使用的限制、配置变更、数据迁移和恢复方式。

文档同步规则：

| 改动 | 同步位置 |
| --- | --- |
| 安装、配置、启动方式 | README 和相关使用说明 |
| 用户可见行为或范围 | requirements.md |
| 模块、接口、任务状态 | architecture.md |
| 里程碑和交付范围 | roadmap.md |
| 权限、密钥、数据策略 | security.md |
| 电脑接口和能力差异 | cloud-computer.md |
| 服务器、网络、费用和部署 | infrastructure.md |
| PC 页面与组件交互 | frontend.md |
| 重要选型或架构取舍 | docs/adr/ |

## 8. 提交说明

提交说明用中文，分点列，一条一行写清具体改了什么。避免只写“更新”“修复问题”等无法评审的描述。

示例：

```text
1、新增任务状态持久化，支持重启后识别中断任务
2、限制文件工具访问范围，拒绝工作区外的路径
3、补充授权拒绝和执行取消的验收用例
```

此格式用于用户授权后的实际提交，不代表可以自行提交。
